# Candidate review sessions

`POST /api/candidates/review-sessions` requires `candidates:read`. Supply an idempotency UUID and the list's base filters (`status`, `authorId`, `search`, `sourceLanguage`, `fetchedAfter`, `fetchedBefore`). Group, page size and cursor do not form the base filter. The response explicitly contains only `sessionId`, `expiresAt` and three group counts.

The server materializes candidate IDs, group and rank once with `INSERT SELECT`. Positive-tag or current-model winning positive evidence enters priority; a deprioritizing tag conflicts into uncertain and sorts first there. Without positives, deprioritizing tags or all-image valid low-class results enter low priority. Remaining items are uncertain. Historical manga/photo and the cached single disposition do not route candidates. Current adapter taxonomy and policy are SQL parameters, never identifiers.

Pass `reviewSessionId` and the same base filters to `GET /api/candidates`. All groups share the session; each group has its own opaque cursor. Members and ordering remain stable while cards, permissions, author archival and human review status remain current. Each request hydrates at most the requested page (maximum 100); total and pending-work metadata are computed in SQL. Session creation still sorts and stores the complete eligible membership and is not O(page).

Sessions expire after 30 idle minutes or two hours total. Reads renew at most once every five minutes. Model/filter changes produce 409; expired sessions produce 410. Signed v2 ordinal cursors bind session, filter, model and group; the per-session signing secret is stored only in the database and never returned. Cursors do not grant permission. Existing clients without a session use live SQL keyset pagination; old UUID cursors now receive an explicit 400 version error and must restart at the first page. Live mutable scores can still move across a keyset boundary; use a review session for stable review.

`replaceSessionId` atomically replaces an owned session only after the new snapshot succeeds. Creation and idempotency are serialized by actor. At most three active sessions are retained per actor; a fourth without a replacement evicts the least recently used session. More than 50,000 matching candidates produces an explicit narrowing error and rolls back the new snapshot and replacement. Worker maintenance deletes at most 2,000 expired entries and 20 empty sessions per minute; session deletion cannot cascade a large populated snapshot.

The web candidate scope creates one session shared by its three groups. Background analysis and source-sync completion rehydrate current cards. The compact **刷新列表** action replaces membership/rank, while **同步图源** retains its collection action. Selection stores candidate ID and the first observed revision across pages, replacement and expiry. Explicit base-filter changes clear selection. Bulk results remove only `succeeded` and `unchanged`; failed, conflicted and omitted results stay selected for inspection.

Integration fixtures require a separate `_test` PostgreSQL database and clean only their owned users/authors/candidates/sessions. Synthetic scale measurements should include snapshot sorting/materialization, 24-item hydration/JSON size and Node heap, ordinal-page plans and bounded cleanup at 1k/10k/50k. These measurements do not establish real-model or production throughput.

## Routing evidence snapshot

Session format 2 freezes the three-group routing result, original hashtags and both tag-rule directions in each entry reasonJson. A single MVCC rule query captures aliases plus group metadata; its immutable parameters drive both grouping and reason generation in one INSERT SELECT. The session stores a rule hash and adapter routing-policy hash. Rule edits and background inference do not invalidate current membership or replace its explanations. Format 1 sessions require an explicit refresh; historical classification rows remain unchanged. Current model identity and filters still fence session reads.
