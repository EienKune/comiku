# 群通知

通知模块提供持久事件登记、QQ群目标与事件开关、消息预览、发送测试及投递处理。平台通过 OneBot v11 HTTP 主动调用 NapCat 等兼容实现，机器人继续由部署者管理；无需为了发通知再启动一个机器人框架。

作品核心流转通过已有持久 WorkEvent 异步接入。业务服务继续只执行原有业务与事件保存，不调用机器人或通知登记服务；通知后台在独立事务中补账、入队和投递。默认关闭，启用后从首次启动补账的持久起点接收新的受支持事件，不自动群发起点之前的历史。

认领仅表示加入翻译、校对或嵌字职责，不直接改变制作状态；首次实际编辑、嵌字交接和阶段提交分别形成开始与流转通知。运营通过发布权限确认发布，不是第四个可认领职责。审核是独立状态轴，不把“需要审核”当作固定制作步骤。

## 配置连接

默认关闭通知，不运行通知维护/消费循环，不请求机器人。API 和 worker 使用相同的私有配置；配置文件放在仓库和镜像构建上下文之外。

```dotenv
NOTIFICATIONS_ENABLED=true
NOTIFICATION_CONNECTIONS_FILE=/absolute/private/notification-connections.json
COMIKU_QQ_BOT_TOKEN=replace-in-private-environment
```

文件支持连接数组或 `{ "connections": [...] }`，最多 8 个连接、64 KiB。示例只包含占位地址和环境变量名称，不要在公开文件中填实际凭据。

```json
{
  "connections": [
    {
      "key": "team-qq",
      "name": "团队机器人",
      "adapter": "onebot-http",
      "endpoint": "http://127.0.0.1:3001",
      "tokenEnv": "COMIKU_QQ_BOT_TOKEN",
      "allowedIps": ["127.0.0.1"]
    }
  ]
}
```

连接文件只能由部署者维护，网页不接受任意 endpoint、headers、token 或 action。API 只返回连接名称和是否可用，不回显 URL、密钥或内部指纹。坏文件或某连接配置错误会使通知不可用，不触发机器人探测，也不会把私密解析错误传给业务接口。

HTTP 只允许显式许可的 loopback/私网地址；公网连接使用 HTTPS。DNS 返回的所有地址都必须在精确 allowedIps 内；请求固定连接经过验证的地址，不跟随重定向、不继承环境代理。metadata、链路本地、多播和未指定地址始终拒绝，HTTPS 使用正常证书验证。总超时 5 秒、响应最多 64 KiB，连接池随应用关闭释放。

连接配置按进程启动时读取。换 endpoint、token 或允许 IP 后，重启通知相关 API/worker 以采用新配置，再在系统管理中重新保存对应群目标，确认新的连接代次。旧投递不会自动改用新连接。先停用目标并等待在途请求结束，可使轮换边界更清晰；未确认的在途发送按未知结果处理。

## 系统管理

在系统管理的“推送通知”页签管理，分为群订阅、消息模板、投递记录和运行状态。只有当前具有 system:manage 的用户可以读取通知配置、投递或登记记录，或执行新增、修改、测试、核对及补发。每群选择连接、群号和事件；有持久职责的事件可以选择不限制职责或指定职责。未知职责只匹配不限制的规则，不按作品当前状态推断。新群默认停用、事件空选；启用必须选择事件。

24种业务事件各有一份公共结构化模板。作品标题、作者、操作人分别开关，默认均关闭；最多120个Unicode码点的提示语独立于三个开关。标题与编号同一行，业务动作另起一行；入库作者放在动作前，其他事件仅在作者开关开启时展示。操作人按事件显示为入库人、保存人、提交人等；认领或加入协作直接进入动作句，不重复姓名。关闭开关或缺资料时不显示相应名称，不改写已有模板或旧群的显示选择。

时间固定使用北京时间（`Asia/Shanghai`），格式为 `YYYY-MM-DD HH:mm:ss`，不随服务器时区变化。正文按事件目的表达，不附通用职责、流程或内容审核状态行。资料保存只表示“作品资料已保存”，不推断具体字段变化；翻译提交表示待校对，校对提交表示待嵌字，嵌字完成表示待发布。认领不表示开工，成图上传不表示嵌字完成，个人分工完成不表示整个阶段已提交。

内容审核判断原作内容是否符合团队规则、是否继续制作，独立于翻译校对和图片模型识别。申请显示“制作已暂停，原作内容待确认”；确认继续显示“已确认继续制作”；撤回显示“已撤销内容审核申请，继续制作”。归档和恢复仅描述作品动作，不猜测审核处置原因。消息不包含审核理由、未捕获的版本号或具体字段变化。

```text
【Comiku 通知】
#12 示例作品
翻译已提交，待校对
发生时间：2026-11-10 20:43:01
提交人：示例成员
登录后查看：https://comiku.example/works/00000000-0000-4000-8000-000000000001
```

正文按Unicode码点计数，含历史补发标记不超过1000码点。长度紧张时依次为标题、作者、操作人和提示语分配空间，必要时截断可选内容；编号、业务动作、时间与完整链接不截断，固定内容也无法容纳时明确拒绝。预览、保存后的样例与业务通知共用同一排版；预览不保存、不发送。旧群legacy正文继续使用原布局和ISO时间；已冻结的消息（包括待发消息）与历史补发不会重新排版。

保存模板只影响之后首次成功捕获的通知，不更改旧正文，不取消已登记的队列。模板内容修订、管理并发revision和群受众代次独立。旧群保持原详情开关，需明确预览并切换为事件模板；切换不改变受众代次或取消旧待发，新建群默认使用事件模板。

旧群采用模板时，保存请求必须携带预览中全部所选事件的模板修订。服务端在同一事务中按“模板锁→群锁”顺序校验；其他管理员在预览后修改模板时，采用返回409并保留草稿，须重新预览确认。前端刷新和群配置版本校验不能替代这项模板修订校验；已采用的群后续仍正常跟随公共模板修改。

“发送样例”使用已保存群配置、指定事件和职责及合成资料，确认目标与正文后排队。保存配置和预览都不发送；返回排队不等于群内已收到。旧客户端不能用详情总开关覆盖已采用事件模板的配置。

图源采集与推送页签切换保留未保存草稿和展开状态，非激活面板暂停查询。连接“可用”表示本机配置通过校验，不表示机器人当前在线或群内可发送。

默认消息包含编号、动作、发生时间及需要登录的站内详情链接。额外内容使用固定白名单；不会把审核理由、内部备注、授权凭证、原图、签名 URL 或任意 WorkEvent.detail 发到群里。用户文字编码为 OneBot text 段，文字中的 CQ 码不会触发图片或 @全体。

停用、改群、连接或更改事件/职责订阅会推进受众代次，取消该群旧代全部未发送记录并保留原因，包括仍符合新订阅的消息；重新启用只接收新起点后匹配的事件，不倒灌历史。全局运行开关关闭则暂停后台处理并保留既有待办。已通过发送边界的在途请求仍可能完成，关闭开关无法召回已在网络中的消息。

原样保存不会生成新投递策略，仅修改群目标的显示名也不会取消待办。管理页面使用的 revision 与后台投递代次承担不同职责：前者防止多人覆盖编辑，后者控制是否允许继续向原受众发送。

## 事件登记接口

模块导出 NotificationPublisherService，供其他受控集成通过公开接口接入，不依赖机器人协议或群号。没有任意发布业务事件的管理 HTTP 端点。下列同事务接口仍可使用，但作品默认接入选择异步补账，不把通知写入作为作品提交成功的额外条件。

```ts
await publisher.recordTx(tx, {
  eventKey: `work-event:${sourceEventId}`,
  type: "stage_submitted",
  resourceId: workId,
  aggregateVersion: savedWorkRevision,
  ordinal: 0,
  occurredAt: occurredAt,
  workNumber: workNumber,
  stage: "translate",
  fromWorkflowStatus: "translating",
  toWorkflowStatus: "pending_proofread",
});
```

recordTx 只执行数据库查询和登记，可与业务提交原子保存；失败向调用方返回，不静默漏记。它保存登记时生效的群订阅与原目标快照，异步路由不按后来的群配置改写历史。相同 eventKey 与相同归一化数据返回原事件；同 key 的不同内容冲突。不要在业务重试时换新 key 或重新生成发生时间。

record(event) 在独立事务中登记，并对可重试的数据库事务冲突作有限重试。它不保证与之前另一个业务事务原子；业务已提交、进程在调用 record 前退出仍会漏事件。需要可靠关联时应使用 recordTx，或另行设计具备持久来源的补账流程，不能用 fire-and-forget 或扫描时间游标替代。

当前事件目录覆盖下表24种已有持久业务动作，类型复用生成的 WorkEventAction。新增目录不会自动修改现有群的事件或职责订阅，管理员须明确选择。个人贡献完成只表示本人负责部分已完成，不等于整个阶段提交。自动保存、逐图识别和作者变化不在此目录。直接调用方提供聚合版本与事务内 ordinal；同群同资源按已登记顺序处理，不承诺任意延迟外部登记仍能恢复全局因果顺序。

## 作品事件异步补账

原有业务事务已经保存 WorkEvent。通知后台反复查找受支持且尚未捕获的源行，每批最多 50 项，逐项在短事务中保存独立 receipt、安全输入及受众快照，同时更新源的捕获标记。另一短事务幂等创建 NotificationEvent 并将 receipt 标记为已登记。固定业务 key 为 `work-event:<sourceId>`，两处提交之间退出都能继续，无需重做作品操作。

旧15种和新9种未捕获集合分别使用 partial index；每路按自己的起点各取至多一条候选，再按发生时间和ID选择本次捕获，短事务最多锁住两条候选。这样原目录查询不会反复过滤扩展前的新9种历史；不支持的源不扫描。新增索引仍有有限的存储、写入和WAL开销。不把随机 UUID 或 createdAt 高水位当成已消费进度。较早发生但较晚提交的源，只要属于持久起点之后，仍可被发现。原15种事件使用持久 `work-events-v1` 起点；新增9种资料、协作、署名、贡献、译文导入与成图版本事件使用首次新版补账维护建立的独立 `work-events-expanded-v1` 起点，同时仍受原起点约束。两个起点重启或全局暂停都不会重置；扩展前的新9种旧历史不自动补发，也不修改其源行标记。

登记阶段没有外部发送副作用，可恢复的数据库失败持久退避并继续重试，延迟上限五分钟。确定性坏输入、未知版本或 payload hash 冲突隔离并保留记录，不让一个作品阻塞其他作品。receipt 是通知内部账本，目前通过受控 ID 日志及数据库定位；管理页的投递记录从 Delivery 建立后开始，不提供独立 receipt 重试页面。

每个群的 sourceAcceptAfter 随真正的投递代次变化推进。旧积压在尚未捕获时遇到改群、停启或策略变更，可以保守跳过，不补给新受众；已捕获记录继续使用原快照并由现有投递代次门控。仅改名字或原样保存不改变起点。源时间只定义资格边界，不是精确提交时间，跨边界的长事务可能漏推。

现有 WorkEvent 没有历史 revision 或严格顺序号，桥接的 resourceOrdinal 表示捕获顺序，不能还原任意并发事务的业务因果顺序。消息使用源中持久化的动作、前后状态和发生时间；阶段仅白名单提取 detail.stage或事件明确的职责，作品编号来自稳定编号。新增资料与协作事件不读取detail.stage；成图版本事件固定嵌字，译文导入仅允许翻译或校对，stage_*仅允许翻译、校对、嵌字。未知职责仅能匹配不限制职责的订阅，非法职责隔离；不会从作品当前状态猜测。新捕获使用v3安全输入，仅对stage_joined从持久operation白名单投影claim/join到participationKind，以区分认领和加入协作；缺失或未知类别使用中性接取措辞，不回查当前参与关系。v1/v2输入、hash与旧冻结正文保持兼容。detail中的个人署名、页码、版本号、操作说明、文件标识与地址均不会透传。

标题、作者名和原操作人展示名在首次成功捕获时读取并冻结，标注资料观察时点及capture_current来源。这表示补账时资料，不表示事件发生时名称；捕获失败回滚通知侧事务后重试，业务提交保持成功。后续登记、重试、补发不再读取当前资料。旧v1输入和正文保持原含义，不补入这些资料；同一事件投递旧群与新模板群时，各群独立冻结正文，不能把新资料串给旧模式群。不读取审核理由、备注、文件标识、签名地址或任意detail。

第一次捕获同时冻结该群匹配规则、模板完整设置与内容修订、群和连接代次及最终正文；捕获与管理保存通过数据库锁协调，避免拼出不同修订的设置。每个接收群有自己的内容快照。模板变更后积压仍使用原快照。

通知失败不会回滚已经提交的业务。源本身缺失、被删除或缺少历史事实，不能靠补账恢复；共享数据库仍有索引维护、异步标记和通知存储的有限开销。关闭通知时没有源扫描或机器人探测。

## 投递与故障恢复

### 运行状态与事件登记记录

系统管理的“推送通知 → 运行状态”展示最近成功补账维护、捕获和登记的观测时间，以及未捕获源、待登记、等待重试和已隔离的数量。维护记录只说明后台补账进程的近期工作，不表示 QQ 在线、群可发送或成员已收到。超过一分钟没有成功维护记录时显示记录过期；全局关闭、尚未启动和最近维护失败分开显示。

统计是有界快照，每项最多读取最老的1001条，超过1000显示1000+。未启动或全局关闭时不扫描作品源，未捕获数量显示为空；管理员仍可显式查看已有通知账本。摘要只在页面激活且运行开启时每15秒刷新，登记明细通过进入页面、筛选或显式刷新读取，不随已加载页数自动轮询。

事件登记记录支持待登记、等待重试、已隔离、已登记和已跳过筛选，以游标分页显示源事件、作品、受控错误、尝试次数及时间。接口不返回原始safeInput、detail、正文或连接秘密；不能在此页清除源标记或重放事件。已登记只表示进入通知事件账本，实际外发结果继续在“投递记录”核对。已跳过通常表示捕获时没有符合资格的群订阅，后改订阅不会自动重建历史意图。

维护观测在业务事务之外，每轮最多追加一次短写入；观测失败不阻断补账或后续投递。源的原15种和新增9种分别使用独立的partial index与持久起点，两路各取有限候选后合并，避免反复扫描新增事件启用前的旧历史。状态查询也沿用这两路范围。查询仍占用有限的数据库读写和索引存储，不代表无开销或已经完成生产容量验收。

后台使用既有 JobsService 的 network/notifications scope，独立于采集与图片处理槽。事件、投递和尝试是持久记录，Jobs 拥有执行租约；通知模块不另建一套租约引擎。短事务预约发送，提交后调用网络，再用条件写保存回执；网络期间不持业务或投递行锁。

| 状态       | 含义                                                      |
| ---------- | --------------------------------------------------------- |
| pending    | 已登记，等待执行                                          |
| sending    | 已跨越发送预约边界，外部请求可能发生                      |
| retry_wait | 已确定未发送的暂时故障，等待有限重试                      |
| accepted   | 协议返回成功且保存 message_id；不代表所有群成员收到或已读 |
| failed     | 永久拒绝或安全重试次数耗尽，记录保留待处理                |
| unknown    | 超时、断线、异步响应或发送后崩溃等，无法确认结果          |
| cancelled  | 用户停用/改群、权限或配置代次改变，未继续发送             |

同一业务 key、重复路由和多 worker 竞争不会重复建立普通投递。可确认尚未发出的暂时故障有限自动重试；unknown 不自动再发。已有 Job 第三次租约耗尽后可能不再进入 handler，因此维护循环还会有界对账，把遗留 sending 收敛为 unknown。

未知结果只隔离同群同资源的后续投递，其他作品继续。管理员可以标记已核对，或在明确接受可能重复后创建历史补发；原记录和尝试保留，补发操作有独立幂等 key。投递详情显示账本中冻结的原群号和安全连接标识，当前管理名称与原目标分开；改群、改名或移除连接后，不把历史记录改成当前受众，也不回显连接地址或凭据。历史补发保留原正文并增加补发标记，不套用当前模板；新格式为标记预留预算，无法安全追加标记的旧长正文明确拒绝。受众已经改变时不能把历史补发给新群。测试与人工补发发送前重新检查发起人资格；团队业务通知不依赖旧配置人始终在职。

投递记录支持组合筛选状态、原群号、作品编号、事件类型和创建时间。作品编号通过唯一 Work 查询后关联事件资源，包含已归档作品；不存在的编号返回空页，不扫描 JSON 快照。群号和时间筛选使用投递时保存的原值，改群后仍可检索原群历史。时间参数 `createdFrom` / `createdBefore` 要求带时区的 ISO 时间，区间为左闭右开 `[from,before)`；相等或倒序区间无效。事件目录包括24种业务事件和 `notification.test`。

历史接口默认每页20项、最多50项，按创建时间和ID倒序读取至多 `limit+1` 个ID后有界读取正文。v2游标绑定规范化的全部筛选条件和页大小，筛选或页大小变化需从首页开始；旧游标需刷新。接口不执行总数统计或 offset 分页。`work.digest` 表示定时工作摘要，`work.ready` 表示任务交接提醒，分别使用 `work_digest`、`work_ready` 资源；两者都不对应单部作品，作品编号筛选针对作品事件。

原群历史使用群号/创建时间/ID索引，稀少事件使用事件类型/ID索引；未决投递 partial index 排除已核对的终态历史。索引仍有存储、写入和WAL开销，有界查询不等同于任意数据规模或并发下的容量保证。

外发积压与事件登记统计分开：`deliveries` 中的 `pending`、`retryWait`、`sending`、`failedUnresolved`、`unknownUnresolved` 分别最多读取最老1001条，超过1000显示1000+，只包含 `resolvedAt=null` 的未决记录；活跃投递由状态流转保证尚未核对，已核对的失败和未知结果退出待处理统计。最早时间使用投递创建时间。每页投递的 `nextEligibleAt` 通过一次批量排队任务查询计算，取任务 `availableAt` 与投递重试边界的较晚时间；任务未排队、已完成或已耗尽时为空。它表示“下次可调度”，不保证发送或收件时间。接口不返回任务原始 payload 或 lastError。

预览和已保存样例明确标注为示例，连接测试明确标注为测试，均不生成不存在的作品链接。真实业务消息继续保留原作品地址；历史冻结正文和补发正文不会随新预览文案变化。

未决事件和投递不会因时间自动过期或清理。故障后应查看投递记录，处理 failed/unknown 或明确取消。当前不提供历史正文自动清理或摘要合并；规模增长后需增加安全保留/归档策略，不能删除去重证据后重新发送旧事件。

OneBot 标准不提供客户端发送幂等键。站内持久意图可以防丢记、防重复排队，但不能在远端已发、回执丢失时同时严格保证群内恰好收到一次。echo 只是请求关联标识。HTTP 200 仍需检查 status/retcode/message_id；async 不作为成功回执。参见 [v11 HTTP](https://github.com/botuniverse/onebot-11/blob/master/communication/http.md)、[消息 API](https://github.com/botuniverse/onebot-11/blob/master/api/public.md)。

## 验证与扩展

普通测试只使用合成事件和本机协议替身，不访问真实群。数据库测试要求独立 _test 数据库；迁移是追加式，并验证重复部署与无漂移。真实机器人验证应使用专用测试群，分别核对入队、协议回执和群内可见消息。

后台批量有界，外发串行、按群持久限流，关闭时不轮询通知。当前少数群无需 Redis、额外 Python 或完整机器人框架。适配器契约保留独立事件与传输结果，后续可实现 OneBot v12/其他平台、个人身份与 @、批次摘要或催办；每项需单独实现并验收，不在 UI 暴露未实现的平台入口。

## 定时工作提醒

在系统管理的推送通知中开启工作提醒，再为各群选择每日摘要、任务交接提醒、72小时未交稿和是否 @。它们与原作品事件、生日订阅独立；原群总开关仍控制全部推送。默认北京时间09:00、18:00，可配置2至3个时段。每日摘要每群每时段一条，零事项跳过；任务交接提醒独立异步发送，不等待每日摘要。同次摘要一次列出全部符合条件的超时明细，同一人只 @ 一次，不按条数拆到后续时段。交接仍是一项任务一条消息。

- 每日摘要展示翻译、校对、嵌字各阶段的当前作品总量及其中待认领数量，例如“翻译10部（待认领4）”，并统计当前可入库候选。待认领数量以实际可接且无人负责为准，不将提前占位的后续阶段算成当前待接工作。摘要只包含这些数量和已到期的72小时未交稿明细，不展示交接明细。
- “任务交接提醒”指提前认领的职责在上游交稿后具备制作条件，正文直接写“可以开始翻译／校对／嵌字”。例如提前认领校对，等翻译交稿后独立提醒“可以开始校对”；当前已可做才认领不另发这类提醒。提醒经后台有界处理，通常一分钟内登记，不保证收件时间；重启后仍有效且尚未消费的交接继续处理。
- 超时按本轮累计可制作72小时且尚未交稿判断，保存草稿不会重新开始计时。制作暂停、归档或资格暂失期间停表，完成、交稿和退出停止提醒；提交撤回、个人完成失效等新轮次重新计时。每轮每群最多一次，在每日摘要时段完整发送当前超时名单。

计时采用独立持久观测投影，不增加业务事务写入。历史任务从首次启用后的观察开始；两次观察之间证据变化或间隔超过可信边界时，不推算其中的可制作时间，可能延后提醒。此实现不能精确还原上线前或长时间停机期间的全部历史。worker每分钟处理有界批次，无订阅或总开关关闭时不扫描工作计时；活动规模超出单轮处理能力也可能延后。

消息冻结截至时间、任务和联系人；发送前重新检查群配置、任务有效性及QQ绑定版本。解绑、改绑、交稿或退出后取消尚未外发的旧提醒；新版摘要因任务变化或观测过期取消时，确认整个旧事件尚未越过外发边界，可在当前有效时段按最新完整名单重建；历史记录保留，已接收或结果未知的消息不自动重发。交接提醒由独立后台维护处理。QQ来自成员本人绑定，只用作提醒地址，不构成QQ身份或账号所有权证明。自由文本中的CQ码保持普通文字，服务端只允许文本和指定成员的结构化at段，禁止at-all；历史管理接口不新增原始QQ字段。

工作摘要有独立发生记录与幂等键，多worker不会为同群同槽重复登记。启用不追旧时段，重启只补当前仍有效的时段；跨槽摘要取消，已进入外发但结果未知的记录保留unknown且不自动重发。工作摘要与任务交接提醒均不支持手动重放旧正文及旧@，保留核对操作；新版摘要仅在可确认未发送且因任务变化取消时于当前时段重新汇总，交接由后台继续处理仍有效且可确认未发送的事项。原作品历史补发行为保持。外部网络请求在发送准备事务提交后进行。

工作提醒的两个消息预览分别调用后端 `POST /api/notifications/work-reminders/preview`，`kind` 可选 `digest` 或 `ready`，省略时沿用 `digest`。工作摘要提示语只用于每日摘要，任务交接提醒没有额外提示语输入。预览使用合成数据、不发送消息，已经冻结的历史正文不会随此次文案调整改变。

全量工作摘要采用内部fmt3快照，普通通知、旧摘要与交接消息沿用原正文和联系人限制。全量摘要不设业务明细条数或@人数上限，按序列化OneBot请求体保留256KiB资源预算；超过预算明确记录失败，不截断、不登记部分Notice，也不阻挡同群交接和其他群处理。分批取证与写入只限制数据库单次操作大小，完整名单仍在同一条消息发送。
